# 架构详解

## 整体架构

```
                    ┌─────────────┐
                    │   用户输入   │
                    │ (工单/查询)  │
                    └──────┬──────┘
                           │
                    ┌──────▼──────┐
                    │  构建 Prompt  │
                    │ A = 选项1     │
                    │ B = 选项2     │
                    │ C = 选项3     │
                    │ ...Label:    │
                    └──────┬──────┘
                           │
                    ┌──────▼──────┐
                    │ /tokenize    │  验证标签是单 token
                    │ 验证标签     │  拒绝非单 token 标签
                    └──────┬──────┘
                           │
                    ┌──────▼──────┐
                    │  SGLang     │  模型处理 prompt
                    │  前向传播    │  生成 vocabulary-sized logits 向量
                    └──────┬──────┘
                           │
                    ┌──────▼──────┐
                    │  读取 logits │  只取 A/B/C 对应位置的 logits
                    │  忽略其余    │
                    └──────┬──────┘
                           │
                    ┌──────▼──────┐
                    │  受限 Softmax│  在选定 logits 间归一化
                    └──────┬──────┘
                           │
                    ┌──────▼──────┐
                    │  映射回选项   │  A→billing, B→technical...
                    │  返回分布    │  + 阈值判断
                    └─────────────┘
```

## 关键设计决策

### 1. 为什么不直接生成文本

| 步骤 | 文本生成 | 固定答案打分 |
|------|---------|------------|
| Tokenize prompt | ✓ | ✓ |
| 前向传播（第一层） | ✓ | ✓ |
| 获取 next-token logits 向量 | ✓ | ✓ |
| 选择并拼接 token | ✓ | ✗ |
| 更新 KV cache | ✓ | ✗ |
| 重复 N 轮直到停止 | ✓ | ✗ |
| 解析输出文本 | ✓ | ✗ |
| 受限 softmax | ✗ | ✓ |

打分路径在第 3 步就停止了。生成路径需要循环 4-5 步直到输出完整答案。

### 2. 为什么用单字母标签

- `billing` 可能是 1 个 token（Qwen）也可能是 2 个 token（其他 tokenizer）
- `technical support` 几乎必然是多个 token
- 多 token 短语需要序列打分：给第一个 token 打分 → 拼接 → 给下一个打分 → 组合，长度本身变成比较变量
- 单字母标签（A/B/C）保证每个候选只占一个词表位置

### 3. 为什么需要兜底选项

受限 softmax 会在已列选项间分配 100% 概率质量。如果真实答案不在候选列表中，模型仍然会给某个选项分配高概率——这是错误的。

解法：加 `OTHER` 或 `ESCALATE` 标签，当已列选项都不合适时让模型选这个。

### 4. 为什么阈值要写在应用代码里

- 模型只负责返回概率分布
- 下游规则（如"top > 0.80 且领先第二名 > 0.20"）是业务逻辑
- 阈值应该用标注数据评估后确定，写在代码里可测试可调整
- 不把业务规则硬编码到模型中

## 模块职责

| 模块 | 文件 | 职责 |
|------|------|------|
| 决策客户端 | `src/decide.py` | 构建 prompt、验证标签、调用 /v1/score、返回决策 |
| 双路径引擎 | `src/engine.py` | 封装 scoring + generation 两条路径，用于对比 |
| 工具函数 | `src/utils.py` | prompt 构建、标签验证、结果格式化、数据集加载 |
| 基准测试 | `benchmark/run_benchmark.py` | 双线程并行对比延迟和准确率 |

## 数据流

```
应用代码                SGLang 服务
    │                        │
    │── ticket + choices ───→ │
    │                        │── tokenize labels
    │←── token_ids ───────── │
    │                        │
    │── prompt + token_ids ─→│
    │                        │── 前向传播
    │                        │── 读取 logits
    │                        │── softmax
    │←── probabilities ───── │
    │                        │
    │── 阈值判断 → 决策      │
```

应用与模型之间只有两次 HTTP 请求：tokenize + score。无需 WebSocket、无需流式、无需生成循环。
